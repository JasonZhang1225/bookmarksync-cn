# D1 书签身份模型：中枢自有 ID + 各浏览器原生 ID 对照

> 状态：设计稿，未实现。对应计划条目 D1，也是 M4（`:dupN` 依赖顺序）的根本解法。

## 现状与问题

书签的 ID 由“所在文件夹的标题路径 + 规范化网址”拼成，例如 `bookmark_bar:Work:example.com/Docs`；同一文件夹里重复的网址再加 `:dup1`、`:dup2`。这套 ID 不依赖任何浏览器内部数据，所以能跨浏览器直接对上，这是它的优点。代价是：

- **移动 = 删除 + 新增。** 把书签拖到另一个文件夹，ID 就变了。中枢只能看到旧 ID 消失、新 ID 出现。Chrome 里那条书签的 `guid` 和添加日期也会丢失，云同步看到的是一删一建。
- **文件夹改名 = 整个子树删除 + 新增。** 文件夹 ID 由标题组成，子项 ID 又包含文件夹 ID。
- **冲突保护失效。** “修改优先于删除”的检查按 ID 比较，ID 一变就认不出是同一个书签。
- **重复项依赖顺序（M4）。** 同一文件夹里两条相同网址的书签调换顺序，`x` 和 `x:dup1` 也会对调。
- **大量“删除 + 新增”容易触发 S2 的大批量删除暂停**，对正常整理书签的用户来说是误报。

## 目标

1. 移动、改名（包括文件夹改名）在中枢里表现为“修改”，不是删除 + 新增。
2. 写回浏览器时尽量沿用该浏览器原来的原生 ID（Chrome `guid`、Safari `WebBookmarkUUID`、Firefox `guid`），让云同步看到的也是“修改”。
3. 首次升级不丢数据，迁移可回退。

## 方案

### 数据模型

- `BookmarkNode` 增加 `hubId: String`（UUID），作为中枢里真正的主键。现有的路径 ID 改名为 `pathKey`，只用于“第一次见到时”的匹配。
- 新增 `BrowserNodeLink`（SwiftData 模型）：`configId`、`hubId`、`nativeId`、`lastSeenPathKey`、`lastSeenParentNativeId`。一个中枢节点在每个浏览器配置里最多对应一个原生节点。
- `ParsedBookmark` 增加 `nativeId` 和 `parentNativeId`。三个解析器读取时直接带出：Chrome 的 `guid`、Safari 的 `WebBookmarkUUID`、Firefox 的 `guid`。

### 导入时如何匹配

对某个浏览器配置读到的每个原生节点，依次尝试：

1. **按原生 ID**：`BrowserNodeLink` 里已有这个 `nativeId`，就是同一个中枢节点。标题、网址、父节点变了都算“修改”，这样就识别出了移动和改名。
2. **按路径键**：没有对应记录（例如新启用的配置、新建的书签），就用现在的 `pathKey` 去找中枢里同一位置、同一网址的节点，找到就建立对应关系。各浏览器之间就是这样第一次对上的。
3. **都找不到**：作为新增节点，分配新的 `hubId`。

删除的判断改为：上次记录的 `nativeId` 这次不见了。

### 写回时如何保留原生 ID

写入某个浏览器时，中枢节点如果已经有对应的 `nativeId`，就原地更新那个原生节点，包括移动到新的父节点。没有的才新建，并把新生成的原生 ID 记进对应表。Firefox 的增量写入（S3）已经是“按 ID 原地更新”的结构，只需要把匹配键从路径 ID 换成 `guid`。Chrome、Safari 的写入器现在靠“路径 ID → 原 GUID”的映射保留 GUID，改成直接按 `nativeId` 查即可。

### 冲突规则（沿用现有原则）

- 修改优先于删除：一边删除、另一边修改（包括移动），保留节点。
- 两边同时修改同一字段：以离上次同步更近的那一边为准；时间相同就按浏览器的固定优先级处理，并在活动记录里提示。
- 两边同时移动到不同文件夹：同上，后发生的为准。

### 迁移

1. 加入 `hubId`（迁移时用 UUID 填充）和 `pathKey`（直接复制现有 ID）。
2. 第一次同步时，对每个浏览器配置按路径键（规则 2）建立全部对应关系。这一步只建立对应，不改变任何书签，所以和现在的行为等价。
3. 之后的同步走规则 1。
4. 迁移前自动备份 SwiftData 存储文件；迁移失败时回到路径 ID 模式（本轮不同步，记录错误）。

## 工作量与风险

- 改动面大：模型、三个解析器的读和写、同步引擎的导入和导出、迁移，相关测试都要改。估计 3–4 个 PR。
- 风险最高的是“第一次按路径键建立对应关系”这一步。需要用真实书签文件的副本（放在 `.artifacts/`）做往返测试：迁移前后各读一遍，应当完全一致。
- Safari 的 `WebBookmarkUUID` 会被 iCloud 改写吗？没有实测证据，要在 C2 实测里确认。如果会，Safari 就只能退回按路径键匹配。

## 建议的实施顺序

1. 解析器带出 `nativeId`，先只记录、不使用（不改变行为）。
2. 引入 `BrowserNodeLink`，导入阶段按原生 ID 识别移动和改名，导出仍按现有方式。
3. 写入器改为按 `nativeId` 原地更新。
4. 删掉路径 ID 作为主键的旧逻辑。

每一步都能单独上线，出问题可以停在上一步。
