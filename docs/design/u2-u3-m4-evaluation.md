# U2、U3、M4 评估

> 状态：评估结论与方案选项，需要用户决定的地方已标出。

## U2 删除归档文件夹 `Deleted by BookmarkSync`

### 现状

在一个浏览器里删除书签后，其他浏览器里的同一条书签不会直接删掉，而是被移进根目录下的 `Deleted by BookmarkSync` 文件夹（Chrome 和 Safari 是这样；Firefox 一直是直接删除，S3 之后还会给 Firefox Sync 留删除记录）。这个文件夹：

- 只增不减；
- 会随 Chrome 同步 / iCloud 出现在手机等其他设备上；
- 读取时会被跳过，不参与同步。

### 为什么当初要它

防止删错：万一读取异常导致误删，书签还在浏览器里，可以手动找回。现在有了 S1（读取异常不算删除）、S2（大批量删除先暂停）和 B2（带时间戳的备份保留 30 天），误删的兜底已经比当初多了很多。

### 选项

| 选项 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A 维持现状 | 不改 | 最保守 | 文件夹越来越大，手机上也看得到 |
| B 定期清理 | 归档超过 N 天（例如 30 天）的条目自动清掉；菜单栏加“清空归档”按钮 | 保留短期反悔余地，长期不堆积 | 需要记录每条是什么时候被归档的（Chrome 可以写进 `date_modified`；Safari plist 没有日期字段，需要另存记录） |
| C 直接删除 | 设置项“删除方式：归档 / 直接删除”，默认改为直接删除，靠备份找回 | 和浏览器原生行为一致，手机上不会多出文件夹 | 找回要去备份管理里恢复，比在文件夹里拖回来麻烦 |

### 建议

C + 保留“归档”选项：默认直接删除，设置里可以切回归档；同时加上“清空归档”按钮，处理已经积累的旧条目。理由：备份和删除保护已经覆盖了误删风险，归档文件夹出现在所有设备上，对日常使用干扰最大。

**需要用户决定**：默认选 B 还是 C。

## U3 写入队列只在内存中；“自己刚写过的文件 5 秒内忽略”

### 写入队列不持久化

应用退出时，排队中的写入会丢失。评估结论：**不需要改**。下次启动时，导出阶段会重新比较中枢和各浏览器的实际文件，缺的改动会重新算出来、重新排队。中枢本身是持久化的，所以队列只是缓存，丢了可以重建。

### 5 秒内忽略自己写过的文件（`SyncEngine.triggerSync`）

用途是避免“我们写文件 → FSEvents 触发 → 又同步一次”的循环。风险：如果用户恰好在我们写入后 5 秒内改了同一个浏览器的书签，这次文件变化事件会被丢掉。不过下一次任何同步（别的文件变化、应用启动、菜单栏操作）都会按内容重新比较，所以改动不会丢，只是会晚一点同步。

**建议（小改动，可以随下一个相关 PR 做）**：写入时记下写出文件的内容哈希，判断“是不是自己写的”改成比较哈希，不再按时间窗口。这样既不会循环，也不会漏掉用户的改动。优先级低。

## M4 `:dupN` 后缀依赖顺序

### 影响

- 同一文件夹里有两条网址相同的书签，调换顺序后 `x` 和 `x:dup1` 会对调。中枢看到的是两条书签各自“改了标题”，会作为改名同步出去。结果正确，只是活动记录里多两条“更新”。
- 同一层级下有两个同名文件夹，调换顺序后两个文件夹的子树 ID 会整体对调，表现为两边子树的“删除 + 新增”。子项多的话会触发 S2 的暂停，用户确认后结果正确。

### 结论

实际中很少见，而且结果正确，只是噪音大。**不单独修**，由 D1（中枢自有 ID + 原生 ID 对照）彻底解决。在那之前，用户看到的暂停提示里会列出具体条目（B3），能看出是“对调”而不是真删除。
