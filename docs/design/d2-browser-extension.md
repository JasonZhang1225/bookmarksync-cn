# D2 浏览器运行中也能同步：Chromium / Firefox 配套扩展

> 状态：设计稿，未实现。对应计划条目 D2。

## 现状与问题

应用直接改浏览器的书签文件，但浏览器开着时不能写：Chromium 系和 Firefox 运行时把书签放在内存里，退出时会覆盖文件。所以写入要排队，等用户完全退出浏览器（⌘Q）才执行（U1 已在菜单栏提示）。很多人整天开着 Chrome / Edge，改动会一直排着。另外，浏览器自己并不知道文件被改过，云同步收到的改动从它的角度看来路不明（见 C1 待实测项）。

## 目标

浏览器开着时，改动能在几秒内写进去，并且由浏览器自己执行，云同步把它当作正常的用户操作。

## 方案

### 组成

1. **浏览器扩展**（Chromium 用 Manifest V3；Firefox 用 WebExtension，接口几乎一样）。只申请 `bookmarks` 和 `nativeMessaging` 两个权限。
2. **Native Messaging 宿主**：菜单栏应用里附带一个小的命令行程序，扩展通过标准输入输出和它通信，它再通过本机 XPC 或 Unix 套接字转给菜单栏应用。
3. **宿主注册文件**：首次启用时，应用把注册清单写进各浏览器的目录：
   - Chrome：`~/Library/Application Support/Google/Chrome/NativeMessagingHosts/`
   - Edge、Brave 等各有对应目录
   - Firefox：`~/Library/Application Support/Mozilla/NativeMessagingHosts/`

### 数据流

- **浏览器 → 应用**：扩展监听 `bookmarks.onCreated`、`onRemoved`、`onChanged`、`onMoved`、`onChildrenReordered`，把事件连同节点的原生 `id`、`parentId`、`index`、`title`、`url` 发给应用。应用仍以“读取整棵树”为准（扩展可以按需发送 `bookmarks.getTree()` 的结果），事件只用来触发和加速同步。
- **应用 → 浏览器**：导出阶段对“扩展在线”的配置，不再排队写文件，而是把要做的改动（新增 / 修改 / 移动 / 删除）作为操作列表发给扩展，由扩展调用 `bookmarks.create` / `update` / `move` / `remove` 执行，执行结果回传给应用。
- **扩展不在线**（浏览器没开，或没装扩展）：退回现在的改文件方式。

### 与改文件方式共存的规则

- 同一个浏览器配置，同一时间只用一种写入方式：扩展在线就绝不写文件，避免两边互相覆盖。
- 扩展在线时，FSEvents 看到的文件变化同样来自浏览器自己，按现有流程读取即可。
- 扩展上报的原生 `id` 就是 D1 里的 `nativeId`。两者配合，移动和改名都能准确识别。D2 不依赖 D1，但一起做效果最好。

### Safari

Safari 扩展需要随 App 一起签名分发，并经用户在 Safari 设置里启用；它的书签接口也受限。本方案不覆盖 Safari，Safari 继续直接改文件。好在 Safari 写文件的限制比 Chromium 小一些，具体以 C2 实测为准。

## 分发与权限

- Chrome / Edge：上架应用商店需要开发者账号和审核。个人使用可以用“开发者模式”加载未打包的扩展，但每个浏览器配置都要单独装一次。
- Firefox：需要 Mozilla 签名才能长期安装（AMO 上架或自行分发签名）。
- 首次连接时，应用应展示扩展的版本和对应的浏览器配置，由用户确认后才启用写入。

## 风险

- 扩展和应用版本不一致：消息里带协议版本号，不一致时只读不写。
- 大量操作（例如恢复备份后写回几千条）通过扩展逐条执行会很慢：超过阈值时提示用户关闭浏览器，改走文件写入。
- 一个浏览器的多个配置：每个配置各装一份扩展，扩展首次连接时要上报自己是哪个配置（可以用配置目录路径来区分）。

## 建议的实施顺序

1. 只做“浏览器 → 应用”的事件上报，验证连接和配置识别（不写入，风险最低）。
2. 加上“应用 → 浏览器”的写入，先只在 Chromium 上做。
3. 移植到 Firefox。
4. 视 D1 进度，改为按原生 ID 精确更新。
